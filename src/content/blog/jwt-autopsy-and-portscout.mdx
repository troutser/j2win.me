Using nmap or Burp for a while doesn't teach you how they work. So I wrote two small tools that do a fraction of what the real ones do, in code short enough to read in one sitting:

- **[portscout](https://github.com/troutser/portscout)**: an async TCP port scanner in Python, built to learn how nmap decides a port is open, closed or filtered.
- **[jwt-autopsy](https://github.com/troutser/jwt-autopsy)**: a Go CLI that takes JSON Web Tokens apart and explains what's risky about them.

Neither one replaces the real tool. Both are written to be read.

<Callout type="warning" title="legal">
  Only scan hosts you own or have **written permission** to test, and only inspect tokens you're authorized to handle. A
  JWT is often a live credential. Everything below runs against `127.0.0.1` or tokens I made myself.
</Callout>

## portscout

### Open, closed, filtered

A TCP connection starts with a three-way handshake. A port scanner sends the first packet and classifies the port by what comes back:

```text title="the handshake"
scanner --SYN-->      target   "can I connect to port 80?"
scanner <--SYN/ACK--  target   "yes, port 80 is listening"      (open)
        <--RST--               "no, nothing here"               (closed)
        (silence)                                               (filtered)
```

portscout does a **connect scan** (nmap's `-sT`). It asks the OS to `connect()` normally and looks at how that turns out. That means no raw sockets and no root, and since you end up with a real connection you can read a banner off it. The downside is noise: every open port costs a full handshake, and the service will probably log it. nmap's default when run as root is a **SYN scan** (`-sS`), which sends the SYN itself and never finishes the handshake. That's faster and quieter, but it needs raw sockets.

In Python, the three outcomes map almost directly onto exceptions:

```python title="src/portscout/scanner.py"
try:
    # open_connection() performs the full handshake. If it returns, the
    # port accepted our connection.
    reader, writer = await asyncio.wait_for(asyncio.open_connection(target.ip, port), timeout)
except ConnectionRefusedError:
    # The target's TCP stack replied with RST: host reachable, port closed.
    return result(PortState.CLOSED, elapsed_ms())
except TimeoutError:
    # Silence. Our SYN (or their SYN/ACK) was dropped somewhere.
    return result(PortState.FILTERED)
except OSError:
    # e.g. "host/network unreachable": usually an ICMP error from a router
    # or firewall. nmap also reports these as filtered.
    return result(PortState.FILTERED)
```

A **closed** port is actually useful to a scanner, because the RST proves the host is up. **Filtered** means nothing came back, usually because a firewall dropped the packet on purpose so you'd have nothing to work with.

<Callout type="note" title="Windows gotcha">
  When a connection is refused, Windows retries the SYN twice before giving up, so even on `127.0.0.1` a closed port
  takes about 2 seconds to report. Linux answers in under a millisecond. That's why portscout's default timeout is 3s:
  with `-t 1` on Windows, closed ports get misreported as filtered.
</Callout>

### Why asyncio fits

A scan spends nearly all its time waiting for packets. With asyncio, one thread can start hundreds of connects and the event loop resumes each one when its socket answers. The one thing you have to add is a limit, because every connection holds a socket and too many at once hit OS limits or look like a flood. portscout uses a semaphore, and acquires it **before** creating each task, so a huge CIDR scan never has more than `-c` tasks sitting in memory.

You can try the pattern here. This cell fakes the network with `asyncio.sleep` (nothing leaves your browser), so change `CONCURRENCY` and watch how the total time changes:

<Runner
  lang="python"
  title="semaphore_scan.py"
  code={`
import asyncio, random, time

CONCURRENCY = 5
PORTS = list(range(20, 40))
random.seed(1337)

async def fake_connect(port):
    # pretend each handshake takes 50-300 ms; a few ports are "open"
    await asyncio.sleep(random.uniform(0.05, 0.3))
    return "open" if port in (22, 25, 31) else "closed"

async def scan(ports, concurrency):
    sem = asyncio.Semaphore(concurrency)
    results, tasks = {}, []

    async def worker(port):
        try:
            results[port] = await fake_connect(port)
        finally:
            sem.release()

    for port in ports:
        await sem.acquire()          # backpressure: wait for a free slot first
        tasks.append(asyncio.create_task(worker(port)))
    await asyncio.gather(*tasks)
    return results

t0 = time.perf_counter()
res = await scan(PORTS, CONCURRENCY)
dt = time.perf_counter() - t0
print(f"{len(PORTS)} probes, concurrency {CONCURRENCY}: {dt:.2f}s")
for port, state in sorted(res.items()):
    if state == "open":
        print(f"[+] {port}/tcp open")
`}
/>

Set `CONCURRENCY = 1` and it's a plain sequential scan. Set it to 20 and all probes run at once, so the total time drops to roughly the slowest single probe.

## jwt-autopsy

### Base64 is not encryption

A signed JWT is three base64url segments joined by dots: **header**, **payload** and **signature**. The first two are plain JSON that anyone holding the token can read. The signature is the only thing that makes the token trustworthy, and it only helps if the server picks the algorithm and key itself instead of believing what the header says.

This cell decodes a token and runs a few of jwt-autopsy's checks. Paste your own token in (one you're allowed to look at) or edit the header:

<Runner

  title="mini_autopsy.js"
  code={`
const token =
  'eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.' +
  'eyJzdWIiOiJhbGljZSIsInJvbGUiOiJhZG1pbiIsImlhdCI6MTc1ODgwMDAwMH0.';

const b64url = (s) => atob(s.replace(/-/g, '+').replace(/_/g, '/'));
const [h, p, sig] = token.split('.');
const header = JSON.parse(b64url(h));
const payload = JSON.parse(b64url(p));

console.log('header: ', header);
console.log('payload:', payload);

const findings = [];
if (/^none$/i.test(header.alg ?? ''))
  findings.push(['CRITICAL', 'ALG_NONE', 'unsigned token, anyone can forge it']);
else if (!sig)
  findings.push(['CRITICAL', 'SIGNATURE_EMPTY', 'alg is ' + header.alg + ' but there is no signature']);
if (!('exp' in payload)) findings.push(['WARN', 'MISSING_EXP', 'token never expires']);
for (const c of ['aud', 'iss'])
  if (!(c in payload)) findings.push(['INFO', 'MISSING_' + c.toUpperCase(), 'no "' + c + '" claim']);

for (const [sev, code, msg] of findings) console.log('[' + sev + '] ' + code + ': ' + msg);
`}

### The real tool

jwt-autopsy has three subcommands: `decode` pretty-prints the token, `inspect` explains what's risky, and `verify` checks the signature against a key you supply. It uses only the Go standard library, so every check fits in a few lines of `crypto/*` and `encoding/*`.

Here's `inspect` on the same unsigned token:

<Terminal

  host="devbox"

Algorithm:  none (no signature)
Type:       JWT
Signature:  0 bytes

Findings (4):

  [CRITICAL] ALG_NONE: Unsigned token (alg: none)
      The token carries no signature, so anyone can forge or modify it. A
      verifier must never accept "none" for authenticated requests; always
      pin an allow-list of expected algorithms.

  [WARN] MISSING_EXP: No "exp" claim: token never expires
      A stolen token remains usable forever unless the server tracks
      revocation. Short-lived tokens limit the damage of leaks.

  [INFO] MISSING_AUD: No "aud" claim
      Without an audience, a token minted for one service may be accepted by
      another service that trusts the same issuer/key.

  [INFO] MISSING_ISS: No "iss" claim
      Without an issuer, verifiers cannot tell which authority minted the
      token, which matters when several issuers share infrastructure.

These are educational observations, not proof of a vulnerability. See README.md for each code.
`}
/>

There are 27 checks in total. Besides the claim checks there's a `kid` containing `../` or quotes (path traversal or SQL injection if the server trusts it), `jku`/`x5u` headers that point at a remote key, an embedded `jwk`, RSA signatures that imply a key under 2048 bits, and timestamps in milliseconds instead of seconds. The last one is a surprisingly common bug. It pushes `exp` past the year 3000, so the token effectively never expires.

### Algorithm confusion

`verify` refuses to use a key for any algorithm other than its own, and this is the most important design choice in the tool. The attack it prevents goes like this:

1. The server signs tokens with **RS256**. It holds an RSA private key and publishes the public key.
2. The attacker changes the header to `alg: HS256` and signs the token with HMAC, using the **public key bytes** as the secret. Anyone can do this, because the key is public.
3. A naive verifier reads `alg` from the header, sees HS256, and runs HMAC with the only key it has, the RSA public key. The signature matches, so the forged token is accepted.

<Spoiler label="how do you fix it?">
  Bind every key to one algorithm, and never let the token pick. jwt-autopsy refuses to use a PEM public key for `HS*`,
  or a secret for `RS*`/`ES*`/`EdDSA`, and reports `key type does not match algorithm` instead of trying. Your JWT
  library should be configured the same way, with an explicit allow-list of algorithms.
</Spoiler>

## What I took away

- **Writing a small version of a tool is the fastest way to learn the real one.** After portscout, nmap's `filtered` state and its `-sT`/`-sS` flags made sense to me.
- **Explaining matters more than detecting.** Every jwt-autopsy finding says *why* it matters and what a correct verifier does. A finding is an observation about the token. Whether it's exploitable depends on the server that receives it.
- **Tests shouldn't touch the network.** portscout's tests start local asyncio servers (an echo server, a fake SSH greeting, a fake HTTP server) and scan those. jwt-autopsy's tests mint their own signed tokens with a test-only helper.

Both repos are on my GitHub: [portscout](https://github.com/troutser/portscout) and [jwt-autopsy](https://github.com/troutser/jwt-autopsy). The READMEs go deeper, and jwt-autopsy's has a reference table for every finding code.
